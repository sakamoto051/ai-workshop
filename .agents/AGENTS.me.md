# Project Rules

- Antigravity の仕様に関わる内容の場合は、Antigravity公式サイトのドキュメントを情報源として正確な情報を使ってください。
- 公式サイトに記載がない場合は、その旨をユーザーに伝えてください。
- 回答の際は、情報源となった公式ドキュメントのURLも必ず教えてください。
- Antigravity の使い方に関する情報源として、特に https://antigravity.google/docs/cli/overview を使用してください。
- デザインや出力フォーマット、Marpスライドのレイアウト確認に関するルールは、同じディレクトリ内の [DESIGN_RULES.md](./DESIGN_RULES.md) を読み込んで、その内容に必ず従ってください。
- AI関連や技術の変化が激しいトピックについて回答・比較等を行う場合は、必ず `search_web` ツールを使用してその時点での最新情報を取得し、古い知識（学習データ）に頼らず最新の事実に基づいて回答してください。
- 【再発防止】複数のモデルや技術要素を列挙・比較する際は、全体を要約した1回の検索結果だけで推測・補完してはいけません。必ず「個別のモデル名・要素ごと」にピンポイントで検索を行い、それぞれ独立してファクトチェックを行ってください。
- 【推測の厳禁】上位モデルや同世代のモデルが同じスペックだったとしても、「下位モデル（例: HaikuやMini等）も同じだろう」と**類推・推測して数値を埋めることを一切禁じます**。すべての個別の行・モデルに対して、「そのモデル名での検索結果」による裏付けを必須とします。
- 【ミス発生時の基本行動】ユーザーから間違いやミスを指摘された場合、単に謝罪して修正するだけでなく、必ず以下の「再発防止プロセス」を自律的に実行すること。
  1. 原因調査: なぜそのミスが起きたのか、自身の思考プロセスや情報収集の不備を自己分析する。
  2. 再発防止策の立案: 同じ種類のミスを仕組みとして防ぐための、具体的な行動指針を検討する。
  3. ルール化・スキル化: 検討した再発防止策を、本 `AGENTS.md` などのルールファイルに自律的に追記、もしくは必要に応じて新しいスキルとして定義し、システムレベルで二度と同じミスを起こさない状態を確保する。
- 【Marpスライド編集時のレイアウト確認の絶対義務】Marpスライド (`.md`) を編集・修正した際は、いかなる場合でも**必ず** `playwright` MCP または `marp-layout-checker` スキルを使用して画面キャプチャを取得し、レイアウト崩れ（文字のはみ出し、フッターとの重なり等）がないか厳格に目視確認すること。「軽微な重なり」であっても許容せず、完全に枠内に収まるまで`<style scoped>` 等を用いた調整を自己完結で行い、その結果をユーザーに報告すること。
- 【検索サマリーのハルシネーション対策】`search_web` ツールの検索結果（サマリー）は、他のAIツール（CursorやCopilotなど）の仕様を混同してハルシネーション（例: 存在しな　い `.antigravityignore` 等の設定ファイル名を捏造）を起こすリスクがあります。特定の機能や設定ファイルの有無を案内する際は、検索サマリーを鵜呑みにせず、必ず公式ドキュメントの原文を確認するか、複数回のピンポイント検索で事実確認を徹底してください。
- 【出力時の常体ルールの徹底】ユーザーへの応答、およびスライドやコードのテキスト編集を行う際は、必ず事前に `DESIGN_RULES.md` を思い出し、**「です・ます調」が混入していないか（「だ・である調」になっているか）** を出力前にセルフチェックすること。
- 【URLの捏造防止と未記載時の対応】システムプロンプト等から得た内部仕様であっても、公式ドキュメントに記載があるかのようにURLを捏造して回答してはいけない。情報源を提示する際は必ず事前にアクセスして実在と内容を確認し、公式サイトに記載がない場合はルールに従い「公式サイトに記載がない（内部仕様である）」旨を正直に伝えること。
- 【ログ解析の注意点】`Tool calls` のトークン数は「ツール呼び出し時のリクエスト（JSON）のサイズ」のみを示しており、ツール実行結果（レスポンス）のサイズは含まれない。トークン数が少ない（例: 数十トークン）からといって「ツールが実行されていない」と早計に推測してはいけない。必ずトランスクリプトの実ログを確認すること。
