# プロジェクト全体ルール (AGENTS.md)

これはすべてのAIエージェントに適用される巨大なルールブックです。
本プロジェクトで作業するすべてのAIエージェントは、以下のルールを一言一句遵守してください。

---

# 【品質統一化・構造化】アーキテクチャ標準規約

当プロジェクトでは、開発者およびAIによる「オレオレ実装（1ファイルへの全詰め込み等）」を厳しく禁止し、品質と構造の統一化を図るため、以下のディレクトリ構成と責務分割を**強制**します。

機能追加（例：「〇〇機能を追加して」という曖昧な指示）を受けた場合、必ず以下の4層アーキテクチャに従い、複数のファイルに綺麗に分割して実装を展開してください。

## 📁 必須ディレクトリ構造と責務

機能（Feature）ごとに以下のディレクトリを切って実装すること。
単一のファイル（例: `Controller.ts` や `index.ts` など）にDB処理もルーティングも混ぜることは許されません。

1. **`domain/` (ドメイン層)**
   - 責務: ビジネスルール、Entity、カスタムエラーの定義
   - 依存: 他のどの層にも依存しない
   - 生成例: `ReviewEntity.ts`, `ReviewErrors.ts`

2. **`usecase/` (ユースケース層)**
   - 責務: アプリケーションのユースケース進行（データの流れの制御）
   - 依存: domain層のみ
   - 生成例: `SubmitReviewUseCase.ts`, `GetReviewsUseCase.ts`

3. **`presentation/` (プレゼンテーション層)**
   - 責務: リクエストの受け取り（ルーティング）、DTOへの変換、レスポンスの返却
   - 依存: usecase層のみ
   - 生成例: `ReviewController.ts`, `ReviewDto.ts`, `ReviewRoutes.ts`

4. **`infrastructure/` (インフラストラクチャ層)**
   - 責務: データベースや外部APIへの実際のアクセス
   - 依存: domain層で定義されたRepositoryインターフェースを実装する
   - 生成例: `ReviewRepositoryImpl.ts`

## ⚠️ ルール強制（ガバナンス）

- AIは、ユーザーからの指示がどれだけざっくりしたものであっても、**「必ず上記4つの層にファイルを分割」**してコードを出力しなければなりません。
- 「とりあえず動く簡易版を作りました」という言い訳は一切受け付けません。必ず標準化されたエンタープライズ向けの構造を出力してください。
- 層をまたぐ依存（例: presentation層から直接infrastructure層を呼び出す）を発見した場合は、即座にリファクタリング対象としてユーザーに報告してください。

# 社内セキュアコーディングガイドライン

本ガイドラインは、当社が開発するすべてのバックエンドAPIにおいて厳格に遵守されなければなりません。

## 第1条：SQLインジェクション対策

- データベースへのクエリを発行する際、文字列結合（`+` やテンプレートリテラル `${}`）を用いてSQL文を構築することは**固く禁じます**。
- 必ずプレースホルダー（`?` 等）を用いたパラメータ化クエリ（Prepared Statement）を使用してください。
- ORMを使用する場合であっても、`raw()` や `query()` などの生SQL実行メソッドに未検証のユーザー入力を渡してはなりません。

## 第2条：個人情報（PII）の保護と露出禁止

- `users` テーブルなど、個人情報を含むテーブルからデータを取得してAPIのレスポンスとして返す際、以下のカラムは**絶対に含めてはなりません**。
  - `password_hash`
  - `phone_number`
  - `credit_card_id`
  - `my_number`
- 原則として、レスポンス用のDTO（Data Transfer Object）に詰め替えるか、SELECT句で必要なカラムのみを明示的に指定してください。`SELECT *` の使用は推奨されません。

## 第3条：ログ出力時の機密情報マスキング

- ユーザーの検索キーワードやアクセスログを出力する際、個人を特定可能な情報やパスワードがログに平文で書き込まれないよう注意してください。
- トークンやAPIキーがログに含まれる可能性がある場合、必ず先頭4文字以外を `****` でマスキングしてください。

## 第4条：認証・認可の徹底

- すべてのエンドポイントは、明示的に「認証不要」と設計書に記載されていない限り、認証ミドルウェアを通過させてください。
- 認可チェック（そのリソースを操作する権限があるか）は、presentation層ではなくusecase層で行ってください。
- JWTの検証では、署名アルゴリズムとして `none` を許可しない設定になっていることを必ず確認してください。

## 第5条：外部入力のバリデーション

- リクエストボディ、クエリパラメータ、パスパラメータ、HTTPヘッダーのすべてを「信頼できない入力」として扱ってください。
- バリデーションはpresentation層の入口で一度、ドメイン層の生成時にもう一度、**二重に**実施してください。

# 社内TypeScriptコーディング規約

当社のTypeScriptプロジェクトにおいて、型安全性を最大限に担保するため、以下の規約を厳守してください。

## 第1条：any 型の完全禁止

- いかなる理由があっても `any` 型の使用は禁止します。
- 外部APIや動的なデータを扱う場合は、`unknown` 型を使用し、必ずZod等のバリデーションライブラリを用いて型推論（Type Guard）を行ってください。
- `as any` によるキャストの回避も同様に禁止です。型エラーが解決できない場合は、型定義そのものを見直してください。

## 第2条：返り値の型定義の義務

- すべての関数およびクラスメソッドには、必ず明示的な返り値の型（Return Type）を定義してください。
- データベースから取得した結果をそのまま返すのではなく、必ず対応する Entity または DTO のインターフェース/クラスの配列（例: `Promise<UserDto[]>`）として型付けして返却してください。

## 第3条：null / undefined の取り扱い

- `strictNullChecks` を前提とし、`!`（Non-null assertion operator）の使用は原則禁止します。
- 値が存在しない可能性がある場合は、早期リターンまたは `??` / `?.` を用いて明示的に処理してください。

## 第4条：イミュータビリティの原則

- 関数の引数として受け取ったオブジェクトや配列を直接変更（ミューテート）してはなりません。
- 配列操作には `push` / `splice` ではなく、`map` / `filter` / スプレッド構文を優先して使用してください。
- 定数はすべて `const` で宣言し、`let` の使用はループカウンタ等の最小限に留めてください。

## 第5条：命名規則

- クラス名・インターフェース名・型エイリアス: `PascalCase`
- 変数名・関数名: `camelCase`
- 定数（環境変数由来の設定値等）: `SCREAMING_SNAKE_CASE`
- ファイル名: クラスを含む場合は `PascalCase.ts`、それ以外は `kebab-case.ts`
- boolean を返す関数・変数には `is` / `has` / `can` のいずれかのプレフィックスを付けてください。

# ビジネスロジック・非機能要件ガイドライン

当社のバックエンドシステムにおいて、品質とパフォーマンスを担保するため、以下の実装規約を遵守してください。

## 第1条：一覧取得APIにおけるページネーションの強制

- リソースの一覧（リスト）を取得するAPI（例：レビュー一覧、商品一覧など）では、全件取得は**厳禁**とします。
- 必ず `limit` および `offset`（またはカーソルベース）のページネーションを実装し、メモリ枯渇やDBのパフォーマンス劣化を防いでください。
- `limit` のデフォルト値は `20`、最大値は `100` とし、それを超える指定はバリデーションエラーとしてください。

## 第2条：リソース作成（POST）時の一意性・重複チェック

- リソースを作成する際、ビジネス要件として「1ユーザーにつき1件まで」などの制約がある場合（例：同一商品に対する重複レビュー投稿）、DBへ保存する前に必ず重複チェックを行ってください。
- ドメイン層またはユースケース層で、すでにデータが存在するかを確認し、存在する場合は適切なエラー（409 Conflictなど）を返す必要があります。

## 第3条：ドメインオブジェクト内の境界値バリデーション

- エンティティ（ドメインオブジェクト）を生成・更新する際、数値や文字列の境界値バリデーションを必ず実装してください。
- 例：レビューの評価スコア（rating）は `1` から `5` の間に制限し、範囲外の値を受け取った場合はドメイン層で例外（DomainException）をスローしてください。
- 文字列項目には最大文字数を必ず設定してください（例：レビュー本文は 2,000 文字以内）。

## 第4条：トランザクション境界の明確化

- 複数テーブルへの書き込みを伴うユースケースでは、必ずユースケース層でトランザクションを開始・コミット・ロールバックしてください。
- infrastructure層の個別リポジトリ内で暗黙的にトランザクションを張ることは禁止します。

## 第5条：外部API呼び出しの耐障害性

- 外部APIを呼び出す処理には、必ずタイムアウト（デフォルト5秒）を設定してください。
- 一時的な失敗（5xx、タイムアウト）に対しては、指数バックオフ付きで最大3回までリトライしてください。
- リトライしても失敗した場合は、ドメイン例外に変換して呼び出し元へ伝播させてください。

# エラーハンドリング統一規約

## 第1条：例外の階層構造

- すべてのカスタム例外は `AppError` を基底クラスとして継承してください。
- 例外クラスは以下の3系統に分類します。
  - `DomainError`: ビジネスルール違反（400系に対応）
  - `NotFoundError`: リソース不存在（404に対応）
  - `InfrastructureError`: DB・外部API起因の障害（500系に対応）

## 第2条：エラーレスポンスの統一フォーマット

- APIのエラーレスポンスは必ず以下のJSON構造で返却してください。

```json
{
  "error": {
    "code": "REVIEW_ALREADY_EXISTS",
    "message": "この商品にはすでにレビューを投稿済みです。",
    "details": []
  }
}
```

- `code` は `SCREAMING_SNAKE_CASE` の一意なエラーコードとし、エラーコード一覧表に必ず追記してください。
- スタックトレースやSQL文など、内部実装が推測できる情報をレスポンスに含めてはなりません。

## 第3条：握りつぶしの禁止

- `catch` ブロックで例外を捕捉した後、ログも出力せず再スローもしない「握りつぶし」は絶対に禁止します。
- 例外を変換して再スローする場合は、必ず元の例外を `cause` として保持してください。

# テストコード作成規約

## 第1条：テストの必須化

- 新規に作成したusecase層・domain層のコードには、必ずユニットテストを同時に作成してください。
- テストのないプルリクエストはレビュー対象外とします。

## 第2条：テストの構造

- テストは `describe` / `it` を用い、`it` の説明文は「〜の場合、〜を返すこと」の形式で日本語で記述してください。
- 1つの `it` の中で検証する事柄は原則1つとし、Arrange-Act-Assert の3段構成を守ってください。

## 第3条：テストデータとモック

- infrastructure層への依存はすべてインターフェース経由でモック化してください。実DBに接続するユニットテストは禁止です。
- テストデータの生成にはファクトリ関数（例: `createTestReview()`）を用意し、各テストファイルでの手書きコピペを避けてください。

## 第4条：カバレッジ基準

- usecase層・domain層のブランチカバレッジは **80%以上** を維持してください。
- カバレッジを満たすためだけのアサーションなしテスト（いわゆる水増しテスト）は禁止します。

# Git / プルリクエスト運用規約

## 第1条：ブランチ命名規則

- ブランチ名は `feature/チケット番号-概要`、`fix/チケット番号-概要`、`chore/概要` のいずれかの形式としてください。
- `main` ブランチへの直接コミットは禁止です。必ずプルリクエストを経由してください。

## 第2条：コミットメッセージ

- コミットメッセージは Conventional Commits に従い、`feat:` `fix:` `docs:` `refactor:` `test:` `chore:` のいずれかのプレフィックスを付けてください。
- 1コミットには1つの論理的変更のみを含めてください。「ついで修正」の混入は禁止します。

## 第3条：プルリクエストの粒度

- 1つのプルリクエストの差分は原則 **400行以内** に収めてください。
- 400行を超える場合は、リファクタリングと機能追加を分割するなど、レビュー可能な単位に分けてください。

# 【クオリティ保証】社内規約に基づくコードレビュー

当プロジェクトでは、一般的な構文エラーだけでなく、システム全体に致命的な影響を与える脆弱性を防ぐため、静的なセキュリティガイドラインを厳格に適用します。

## 🔍 必須アクション

コードのレビューを依頼された場合、必ず以下の手順を踏んでください。

1. **本ルールブックの全条項をチェックリスト化**:
   上記のアーキテクチャ標準規約・セキュアコーディングガイドライン・TypeScriptコーディング規約・ビジネスロジックガイドライン・エラーハンドリング規約・テスト規約のすべてを照合対象としてください。
2. **規約違反の指摘**:
   もし1つでも違反している箇所があれば、**「🚨 当社のガイドライン第〇条に違反しています」**という形式で条番号を明示して指摘し、修正コードを提示してください。
3. **甘いレビューの禁止**:
   「コードはきれいです」「一見問題なさそうです」といった表面的なレビューは不要です。バグや仕様漏れを見逃して本番にデプロイされた場合、甚大な被害が発生することを肝に銘じてください。
4. **指摘の優先度付け**:
   指摘には `[Critical]` `[Major]` `[Minor]` のラベルを付け、Critical が1件でもあればレビュー結果を「差し戻し」としてください。

# ドキュメンテーション規約

## 第1条：READMEの維持

- 新しい環境変数・起動手順・依存サービスを追加した場合、必ず同一プルリクエスト内で `README.md` を更新してください。

## 第2条：APIドキュメント

- 新規エンドポイントを追加した場合、OpenAPI定義（`openapi.yaml`）へ必ず追記してください。
- リクエスト/レスポンスの例は、実際に動作確認した値を記載してください。

## 第3条：ADR（Architecture Decision Record）

- アーキテクチャ上の重要な意思決定（ライブラリ選定、層構造の変更等）を行った場合、`docs/adr/` 配下に記録を残してください。
- ADRには「背景」「決定内容」「検討した代替案」「トレードオフ」の4項目を必ず含めてください。

# 【Agentic Workflow】実装・監査・修正の自律ループ

あなたはテックリードとして、機能の実装から品質保証までの一連のワークフローを自律的に進行します。
ユーザーから「一気通貫フローをお願い」と指示された場合、以下の3つのフェーズを**ユーザーの指示を待たずに連続して実行**してください。

## 🔄 フェーズ1：機能の実装

1. アーキテクチャ標準規約に従い、ユーザーが要求した機能を `src/` 配下に実装してください。

## 🔄 フェーズ2：コードの自動監査

1. 実装が完了したら、自律的に監査フェーズに移行します。
2. 本ルールブックの全規約をチェックリストとして、フェーズ1で実装したコードの自己レビューを行ってください。
3. レビュー結果として、仕様漏れや規約違反をリストアップします。

## 🔄 フェーズ3：自己修復と最終納品

1. フェーズ2でリストアップした指摘事項をすべて修正し、アーキテクチャの規約を維持したままコードを再実装（リファクタリング）してください。
2. 全ての規約を満たす完璧な状態になったことを確認し、ユーザーに最終結果を報告して完了します。

> **⚠️ 注意事項**: この一連のフロー中、ユーザーに途中で「実装しました、次はどうしますか？」と尋ねないでください。フェーズ3の最終納品まで一気に完了させてください。
