# 社内セキュアコーディングガイドライン

本ガイドラインは、当社が開発するすべてのバックエンドAPIにおいて厳格に遵守されなければなりません。

## 第1条：SQLインジェクション対策

- データベースへのクエリを発行する際、文字列結合（`+` やテンプレートリテラル `${}`）を用いてSQL文を構築することは**固く禁じます**。
- 必ずプレースホルダー（`?` 等）を用いたパラメータ化クエリ（Prepared Statement）を使用してください。
- ORMを使用する場合であっても、`raw()` や `query()` などの生SQL実行メソッドに未検証のユーザー入力を渡してはなりません。

## 第2条：個人情報（PII）の保護と露出禁止

- `users` テーブルなど、個人情報を含むテーブルからデータを取得してAPIのレスポンスとして返す際、以下のカラムは**絶対に含めてはなりません**。
  - `password_hash`
  - `phone_number`
  - `credit_card_id`
  - `my_number`
- 原則として、レスポンス用のDTO（Data Transfer Object）に詰め替えるか、SELECT句で必要なカラムのみを明示的に指定してください。`SELECT *` の使用は推奨されません。

## 第3条：ログ出力時の機密情報マスキング

- ユーザーの検索キーワードやアクセスログを出力する際、個人を特定可能な情報やパスワードがログに平文で書き込まれないよう注意してください。
- トークンやAPIキーがログに含まれる可能性がある場合、必ず先頭4文字以外を `****` でマスキングしてください。

## 第4条：認証・認可の徹底

- すべてのエンドポイントは、明示的に「認証不要」と設計書に記載されていない限り、認証ミドルウェアを通過させてください。
- 認可チェック（そのリソースを操作する権限があるか）は、presentation層ではなくusecase層で行ってください。
- JWTの検証では、署名アルゴリズムとして `none` を許可しない設定になっていることを必ず確認してください。

## 第5条：外部入力のバリデーション

- リクエストボディ、クエリパラメータ、パスパラメータ、HTTPヘッダーのすべてを「信頼できない入力」として扱ってください。
- バリデーションはpresentation層の入口で一度、ドメイン層の生成時にもう一度、**二重に**実施してください。
