## 総合演習: ミニ運用キット (30 分)

`hands-on/s6-integration/` を題材に、以下を全部組み合わせる:

1. **`AGENTS.md`** でテスト・lint コマンドを定義
2. **GitHub MCP** を読み込み専用で接続
3. **`/daily-report`** スラッシュコマンドで「今日触ったファイルの要約」
4. **PreToolUse Hook** で本番 DB への接続を含む shell をブロック
5. **PostToolUse Hook** で監査ログを残す

→ 「使えるエージェント環境」 を作りきる

## ROI 測定の 5 軸

「**時間だけで測らない**」。複数軸で見る。

| 軸 | 例 | 計測方法 |
|---|---|---|
| 時間 | タスク完了までの実時間 | Before/After で比較 |
| 品質 | レビュー指摘数、バグ流出率 | リポジトリ統計 |
| 満足度 | 体感負担 | 週次アンケート (5 段階) |
| コスト | API 利用料 + 人件費 | **コスト追跡 UI** から集計 |
| リスク | 自動承認事故件数 | 監査ログから |

## 主流トピック: コスト追跡 (1/2)

各製品ともコスト可視化が成熟してきた:

| 製品 | 確認方法 |
|---|---|
| Antigravity CLI | `/stats` でセッション内トークン数、ダッシュボードで月次 |
| Codex CLI | `/usage` 系、ChatGPT 連動の使用量画面 |
| Claude Code | `/cost`、`ccusage` 等のサードパーティ ツール |

---

## 主流トピック: コスト追跡 (2/2)

**実務 Tip**:
- 大きなコンテキスト (`AGENTS.md` 肥大、不要な MCP) はコスト直撃
- 定期的に「**1 セッション当たりの平均コスト**」をチームで見る
- 高すぎる時は **モデル変更** や **コンテキスト整理** を検討

---

## ROI 測定の落とし穴

- **「使う前 vs 使った後」だけで判断しない**
  - 単に「慣れ」での改善も混ざる
- **時間短縮 = 品質向上ではない**
  - 早くなって雑になった、もある
- **コスト計算を忘れる**
  - API 費 + 人の時間 + 学習コスト
- **チーム差を均す**
  - 個人差が大きい → 中央値で見る

## アンチパターン

- **3 種類のコンテキスト ファイルを別管理** → 3 重メンテで死ぬ
- **MCP を入れすぎ** → ツール選択で迷う
- **Skills を実装の前提に** → 製品依存になる
- **Hooks を重く** → セッション体感が悪化
- **本番リポで `-y` / `--full-auto`** → 事故
- **数字だけ見て品質を見ない** → 雑な開発が定着

## どの製品を選ぶか

「**ぜんぶ揃える必要はない**」が一つの答え。

- 個人作業: 好みで 1 つ。Antigravity で開始するのが軽い
- チーム標準: 議論より **PoC 一週間** で決める
- 比較選定の軸:
  - 認証・課金 / 既存契約
  - サンドボックス強度
  - Hooks / Skills の必要度
  - ベンダロックインの許容度

## 💡 リテラシー Tip #6 (最後)

> **エージェントは「賢い同僚」、新人ではない**

- 同僚に頼むときと同じ作法で頼む
  - コンテキスト、検証手段、報告フォーマット
- でも **自走しすぎる新人** でもある
  - 監視、レビュー、安全網は人間の仕事

「便利な道具」と「危険な自走者」の **両面** を意識して付き合う。
