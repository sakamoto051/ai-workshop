# プロジェクト開発ルール・ガイドライン（究極詳細版・エンタープライズ仕様）

## 1. 全体アーキテクチャ設計とドメイン駆動設計（DDD）の完全徹底
- 本プロジェクトは、レイヤードアーキテクチャをさらに厳格化したオニオンアーキテクチャを採用する。
- 依存の方向性は「プレゼンテーション層／インフラストラクチャ層」から「アプリケーション層」へ、そして「アプリケーション層」から「ドメイン層」へと向かう同心円状の依存のみを許可し、ドメイン層からの外部依存を例外なく禁止する。
- **ドメイン層 (Domain Layer)**
  - エンティティ（Entity）は、生成時に必ずそのビジネス上の制約を満たすようにファクトリメソッド（`create`等）を通してのみインスタンス化を許可する。引数のバリデーションはファクトリ内で行い、不正な状態のエンティティが存在し得ない設計にすること。
  - バリューオブジェクト（Value Object）は、イミュータブル（不変）として設計し、プリミティブ型（stringやnumber等）の直接利用を避け、必ずドメインの意味を持たせたクラスとしてカプセル化する（例：`string`の代わりに`EmailAddress`クラスを使用）。
  - ドメインイベント（Domain Event）を発行する仕組みを組み込み、ドメイン層の状態変化をアプリケーション層のイベントハンドラーで捕捉し、他モジュールへの波及処理（メール送信やログ記録）を疎結合に行うこと。
- **アプリケーション層 (Application Layer)**
  - ユースケース（Use Case）は、特定のトランザクションスクリプトとして記述し、1ユースケースにつき1つのクラス・1つのパブリックメソッド（`execute`や`handle`）のみを持つCommandパターンを強制する。
- **インフラ層 (Infrastructure Layer)**
  - 外部APIへの通信やデータベースアクセスはすべてリポジトリパターン（Repository Pattern）を用いて抽象化し、インターフェースに対する実装（Adapter）として提供する。
  - リポジトリの戻り値はデータベースモデルではなく、必ずドメインエンティティへのマッピング（Data Mapper）を経てからアプリケーション層へ返すこと。

## 2. 極限のコーディング規約・静的解析・型安全性
- TypeScriptの `tsconfig.json` 設定:
  - `strict`: true は当然として、`noUncheckedIndexedAccess`: true を追加し、配列やオブジェクトからのアクセス時に自動で `undefined` 型を付与させることで実行時エラーを撲滅する。
  - `exactOptionalPropertyTypes`: true により、省略可能なプロパティに明示的に `undefined` を代入するアンチパターンを防止する。
- 命名規則の更なる詳細化:
  - ブーリアン型の変数は、必ず `is`, `has`, `should`, `can` のいずれかのプレフィックスから始めること（例：`isVisible`, `hasChildren`）。
  - イベントハンドラの命名は、プロパティ名は `on` ＋イベント名（`onClick`）、実装関数名は `handle` ＋イベント名（`handleClick`）で統一する。
- 関数型プログラミングのパラダイム適用:
  - `for` ループや `while` ループの使用を原則禁止し、`map`, `filter`, `reduce` などの高階関数を使用して宣言的に記述すること。
  - 副作用（Side Effect）を持つ関数と純粋関数（Pure Function）をディレクトリレベルまたは命名で明確に分離し、ロジックのテスト容易性を最大化する。
- エラーハンドリングの標準化:
  - 例外（throw/catch）による制御フローを禁止する。代わりに `Result` 型（Eitherモナド等）を導入し、関数の戻り値として `Result<SuccessType, ErrorType>` を返す設計を強制する。これにより呼び出し元でのエラーハンドリングをコンパイラレベルで強制する。

## 3. フロントエンド実装の詳細設計とパフォーマンス至上主義
- Next.js (App Router) の活用とレンダリング戦略:
  - ページ単位で静的レンダリング（SSG）、サーバーサイドレンダリング（SSR）、インクリメンタル静的再生成（ISR）を慎重に使い分ける。デフォルトはSSG/ISRとし、キャッシュ不可能な動的データを含む部分のみを部分レンダリング（PPR）やクライアントフェッチにフォールバックする。
- 状態管理のアーキテクチャ:
  - コンポーネントツリーの末端での不要な再レンダリングを防ぐため、Context APIを使用した大規模な状態オブジェクトの共有を禁止する。Zustandのスライスパターンを用いて状態を細分化し、必要なプロパティのみをセレクター関数で抽出して購読すること。
- スタイリングとデザインシステム:
  - Tailwind CSSを使用しつつ、デザインエンジニアが策定したデザイントークン（Color, Typography, Spacing）以外の一時的なマジックバリュー（例：`w-[23px]`）の使用をLintルールで禁止する。
  - UIコンポーネントライブラリ（Radix UIやHeadless UI等）を基盤とし、WAI-ARIAガイドライン準拠のアクセシビリティ（キーボードナビゲーション、スクリーンリーダー読み上げ対応）を全コンポーネントで担保する。
- パフォーマンス最適化の具体策:
  - バンドルアナライザ（@next/bundle-analyzer）をCIパイプラインに組み込み、バンドルサイズが規定の閾値（例: First Load JS 150KB）を超えた場合はビルドを失敗させる。
  - ウェブフォントは `next/font` を用いてビルド時に最適化し、フォント読み込みによるCLSを完全にゼロにする。

## 4. バックエンド実装の詳細設計とマイクロサービス指向
- APIコントラクトファースト開発:
  - OpenAPI 3.1（Swagger）を使用して、実装前にAPI仕様を定義する。このYAML/JSONファイルから、バックエンドのバリデーションロジック、フロントエンドのAPIクライアントコード（React Queryのフック含む）を `openapi-generator` 等で自動生成し、手動での型定義による不一致を排除する。
- データベースとキャッシュ戦略:
  - トランザクション分離レベルを要件に応じて適切に設定する（デフォルトは READ COMMITTED、重要な決済処理等は SERIALIZABLE を検討）。
  - クエリの実行計画（EXPLAIN ANALYZE）を分析し、シーケンシャルスキャンが発生している場合はインデックスのチューニングを行う。
  - Redisを用いたマルチレイヤーキャッシュを構築する。マスターデータはメモリ上にキャッシュし、更新時はPub/Subによるキャッシュのパージ（Invalidation）を確実に実装する。
- 非同期アーキテクチャ:
  - イベント駆動アーキテクチャを採用し、重い処理はAmazon SQSやKafkaを利用したメッセージキューイングに委譲する。
  - メッセージの処理は「At-Least-Once（少なくとも1回）」の配信を前提とし、コンシューマー側の処理は冪等性（Idempotency）を必ず担保する（同じメッセージを何度処理しても結果が同じになるようにする）。

## 5. ゼロトラストセキュリティとデータプライバシーの完全化
- 認証機構の強化:
  - パスワードレス認証（FIDO2/WebAuthn）やOAuth 2.0/OpenID Connect（OIDC）を標準とし、レガシーなパスワード認証を残す場合はMFA（多要素認証）を必須化する。
- 機密情報の管理（Secret Management）:
  - ソースコードや環境変数ファイル（.env）にAPIキーを直接記述することを固く禁ずる。AWS Secrets ManagerやHashiCorp Vaultからアプリケーション起動時に動的に注入する仕組みをとる。
- クライアントサイドセキュリティ:
  - Content Security Policy (CSP) ヘッダーを極限まで厳格化し、許可されたドメイン以外のスクリプト実行やリソースの読み込みをブラウザレベルでブロックする。
  - Strict-Transport-Security (HSTS) を適用し、サブドメインを含むすべての通信でHTTPSを強制する。
- プライバシーバイデザイン:
  - GDPRやCCPAに準拠するため、データベース内の個人識別情報（PII）に対しては、行レベルセキュリティ（RLS）や暗号化カプセル化を実施。物理的にデータが流出しても複合不可能な状態を維持する。

## 6. QA・自動テストの極限追及（カバレッジと品質の保証）
- テスト駆動開発（TDD）の必須化:
  - ドメイン層とユースケース層の実装においては、実装コードを書く前に必ず失敗するテストを記述する（Red-Green-Refactor サイクル）。
- カバレッジの絶対基準:
  - ユニットテストのカバレッジは全体で 90% 以上、ドメイン層においては 100% を要求する。カバレッジレポートをPRのコメントに自動投稿し、閾値を下回る場合はマージボタンをロックする。
- ミューテーションテスト:
  - Stryker等のミューテーションテストツールを導入し、テストコード自体の品質を検証する。実装コードの論理演算子（`&&` を `||` に変える等）を自動改変し、それをテストが検知して「失敗」できるかを測定する。
- E2Eテストの高度化:
  - Playwrightを用いて、PC・タブレット・モバイルの各解像度、主要ブラウザ（Chrome, Firefox, Safari）のマトリックスでテストを実行。スクリーンショットのビジュアルリグレッションテストを自動化し、ピクセル単位の差分を検知する。

## 7. Gitブランチ戦略・レビュー・リリースプロセスの自動化
- Conventional CommitsとSemantic Versioningの完全自動化:
  - コミットメッセージからセマンティックバージョニング（SemVer）を自動計算し、リリースPRの作成、CHANGELOG.mdの生成、GitHub Releasesの発行を自動化するツール（Release PleaseやSemantic Release）を利用する。
- コードレビューのチェックリスト（必須項目）:
  - セキュリティ: SQLインジェクション、XSS、認可バイパスのリスクはないか。
  - パフォーマンス: ループ内でのDBアクセス（N+1）や、不必要な再レンダリングはないか。
  - 設計: 単一責任の原則（SRP）、オープン・クローズドの原則（OCP）に違反していないか。
  - テスト: 正常系だけでなく、エッジケースや異常系のテストが網羅されているか。
- デプロイとロールバック:
  - すべてのデプロイメントはカナリアリリースで行う。最初の1%のトラフィックを新バージョンに流し、Datadog等のメトリクス（エラーレート、レイテンシ）を5分間監視。異常がなければ段階的に100%まで拡張し、異常を検知した瞬間、自動で旧バージョンへルーティングを戻す（Automated Canary Analysis）。

## 8. インフラストラクチャ・オブザーバビリティ・カオスエンジニアリング
- Infrastructure as Code (IaC) と Immutable Infrastructure:
  - TerraformやAWS CDKを用いてインフラを100%コード化し、ドリフト（コードと実際のインフラの差分）を日次で監視する。
  - サーバーインスタンスにSSHでログインして手動設定を変更することを物理的に禁止する（Immutable Infrastructure）。
- 分散トレーシングとログの相関付け:
  - OpenTelemetryを全面採用。フロントエンドで生成されたTrace IDを、HTTPヘッダー経由でバックエンドの各マイクロサービス、さらには非同期メッセージキューにまで伝播させる。
  - すべてのログに `trace_id` を付与し、1つのユーザーアクションによって引き起こされた全システムのログを瞬時に串刺しで検索・可視化できる基盤（Datadog APM 等）を構築する。
- カオスエンジニアリング:
  - 本番環境（または本番と同等のステージング環境）において、Chaos Mesh等のツールを用いて「ネットワーク遅延の発生」「ランダムなPodの削除」「データベースのフェイルオーバー」を意図的に引き起こし、システムの回復力（レジリエンス）と自動復旧プロセスを継続的にテストする。

## 9. ドキュメンテーションとナレッジマネジメントの徹底
- Architecture Decision Records (ADR) の運用:
  - 「どのような技術選定をしたか」だけでなく、「なぜ他の代替案を棄却したか」というコンテキストをMADR (Markdown Any Decision Records) フォーマットで克明に記録し、GitHubの管理下に置く。
- Doc-as-Code:
  - APIドキュメント、アーキテクチャ図（Mermaid.jsを利用）、システム要件定義はすべてソースコードと同一のリポジトリ内でMarkdown/PlantUMLとして管理し、コードの変更とドキュメントの変更を同一PR内で義務付ける。
- コミュニケーションの規約:
  - すべてのドキュメント、コメント、プルリクエストの議論は、解釈の揺れを防ぐため「だ・である調（常体）」を使用し、絵文字や感嘆符の乱用を禁止してプロフェッショナルな記述を徹底する。
