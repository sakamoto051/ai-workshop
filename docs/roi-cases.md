# ROI ケース集

ワークショップで使う実事例 5 つ。各セッションで引用される元データ。
**Before / After / 主観的負担** の 3 軸で整理。

> 数値は社内利用想定のレンジ（チーム規模・案件難度で大きく揺れる）。
> 講師は自分の業務でキャリブレーションしてから提示すること。

---

## #1: コードレビュー前の Self-review

**シーン**: 開発者が PR を出す前に、変更内容を整理して Reviewer に説明する。

| 観点 | Before | After |
|---|---|---|
| 所要時間 | 20〜40 分 / PR | 5〜10 分 / PR |
| 出力 | 簡素な PR タイトル + 「修正しました」程度 | Why / What / Test plan が揃った本文 |
| 主観的負担 | 「説明文を書くのが地味にツラい」 | エージェントが diff から下書きを作り、人間は校正 |

**仕組み**: S4 で扱う `/pr-draft` カスタムコマンド + `git diff --staged`

**注意**: 機密に触れる diff は流す前に確認。レビューア視点の **背景文脈** は人間が補う。

---

## #2: 議事録 → タスク化

**シーン**: 定例会議の議事録から、Issue / TODO を起票する。

| 観点 | Before | After |
|---|---|---|
| 所要時間 | 30〜60 分（会議後） | 10 分前後 |
| 出力 | 起票漏れあり、フォーマットがバラつく | 規定のテンプレで Issue 化、URL を議事録に逆参照 |
| 主観的負担 | 「議事録を読み返すのがダルい」 | 議事録を渡すと候補リストが出てくる |

**仕組み**: S3 で扱う MCP (Notion / GitHub) で議事録を読んで Issue を起票

**注意**: 自動起票は **下書きまで**。最終確認は人間が必ず行う。

---

## #3: 古い API の一括置換

**シーン**: 非推奨化された API を 50〜100 ファイルで置き換える。

| 観点 | Before | After |
|---|---|---|
| 所要時間 | 半日〜1 日 | 1〜2 時間 |
| 出力 | 機械的置換 + 漏れあり | コンテキストを見て置換 + テスト追記 |
| 主観的負担 | 「集中力が持たない作業」 | 進行はエージェント、人間はレビュー |

**仕組み**: S2 のプロンプト設計（タスク分解）+ コンテキスト管理 (`AGENTS.md` でルール明示)

**注意**: 大きな置換は **段階的に**。1 バッチ = 5〜10 ファイル程度で diff を確認する。

---

## #4: 新メンバーのオンボーディング

**シーン**: チームに参加した新メンバーがビルド・テスト・規約を把握するまでの時間。

| 観点 | Before | After |
|---|---|---|
| 所要時間 | 1 日〜数日 | 数時間（自走可能） |
| 出力 | 先輩への質問が頻発、属人化 | エージェントが `AGENTS.md` を元に即答 |
| 主観的負担 | 質問する側もされる側もコスト | エージェントに聞いて先輩は確認役 |

**仕組み**: S2 で扱う `AGENTS.md` / `AGENTS.md` の整備

**注意**: コンテキストファイル自体の鮮度管理が必要。**月 1 回はメンテ** する運用。

---

## #5: インシデント調査

**シーン**: 障害発生時の時系列まとめ + 原因仮説の列挙。

| 観点 | Before | After |
|---|---|---|
| 所要時間 | 2〜4 時間 | 30 分〜1 時間 |
| 出力 | ログを目視で追う、漏れ・順序ミスあり | ログ + git log から時系列を構造化 |
| 主観的負担 | 「過去ログを追うのが消耗する」 | エージェントが叩き台を作る |

**仕組み**: S3 の MCP (Filesystem / Git) + S5 の Hooks（監査ログ）

**注意**: 機微情報を含むログは MCP 経由でも **アクセス範囲を限定**。仮説は人間が裏取り。

## 測定の軸（S6 で使用）

導入後の効果を **何で測るか** をワークショップ末に提示する叩き台:

- **時間軸**: タスク完了までの実時間 (上記 5 ケースの Before/After)
- **品質軸**: PR レビュー指摘数 / バグ流出率 / テスト カバレッジ
- **満足度軸**: チーム内アンケート（週次・5 段階）
- **コスト軸**: API 利用料 / 人件費換算
- **リスク軸**: 自動承認による事故件数（できれば 0 を維持）

「**時間だけで測らない**」がポイント。品質とリスクは別軸でモニタリングする。
