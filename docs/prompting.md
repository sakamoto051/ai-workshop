# プロンプト設計 4 原則

AI エージェントに業務を委任するための基本原則。
S2 で本編、S1/S3/S4/S5 の各ハンズオンで **「悪い指示 → 良い指示」** 対比として登場する。

> 「うまく動かない」の 8 割は **プロンプトの曖昧さ**。
> モデルやツールを変える前に、まず指示を磨く。

---

## 原則 1: 目的を明確に

**悪い**:
> 「このコードをリファクタして」

**良い**:
> 「`calc.py` を関数ごとに分割し、各関数に型ヒントを付けて。
> インターフェースは現状維持」

**なぜ**: 「リファクタ」は人によって意味が違う。エージェントが勝手に解釈すると、
意図しない範囲まで触られる、または逆に何もしないことがある。

**チェック**: 自分の指示を **2 人の別人に渡したとき、同じ結果が返ってくるか**?

---

## 原則 2: コンテキストを与える

**悪い**:
> 「テストを書いて」

**良い**:
> 「`hands-on/s1-basics/calc.py` の `add` / `sub` 関数について、
> pytest で正常系 2 件・異常系 1 件のテストを `tests/test_calc.py` に追加。
> 既存の `conftest.py` のフィクスチャを再利用」

**なぜ**: コンテキストファイル (`AGENTS.md`) + 直接指示で **「どこ・何を・どう」** を埋める。
LLM は文脈がないとそれっぽい一般解を返す。

**コンテキストの 3 層**:

1. **プロジェクト全体** → `AGENTS.md` / `AGENTS.md`
2. **タスク固有** → プロンプト内で言及するファイル / Issue 番号
3. **会話履歴** → 前のターンの内容（直近のものを参照）

---

## 原則 3: 検証可能な形で頼む

**悪い**:
> 「バグを直して」

**良い**:
> 「`test_login.py::test_wrong_password_returns_none` が失敗している。
> `pytest -k test_wrong_password` が緑になるまで修正して」

**なぜ**: 「直った」の **判定基準** をプロンプトに含める。
そうすれば、エージェントは自己検証してから完了報告する。

**検証可能性の具体例**:

- テストコマンド: `pytest tests/`
- リンタ: `ruff check .`
- ビルド: `npm run build`
- 型チェック: `tsc --noEmit`
- 出力比較: 「`./script.py < fixture.json` の結果が `expected.json` と一致」

**注意**: 検証コマンド自体を捏造させない。実在するものを指定する。

---

## 原則 4: 分解する

**悪い**:
> 「認証機能を全部書き直して」

**良い**（段階分解）:
> 1. 「現在の `src/auth/` の構成を読んで、依存関係を箇条書きで」
> 2. 「`login.py` の `authenticate` 関数だけを `bcrypt` ベースに変更。テストも追加」
> 3. 「`logout.py` の Session 破棄ロジックを整理。既存のテストを通す」

**なぜ**: 一度に大きく頼むと、LLM が **「ふんわり全部触る」** モードになり、
レビューしにくく、テストも回らない。

**分解の目安**:

- 1 タスク = **1〜3 ファイル** 程度の変更
- diff が 200 行を超えそうなら、まず計画を立てさせる
- ハンズオンでも **「まず計画 → 確認 → 実装」** のリズムを叩き込む

---

## 「悪い指示 → 良い指示」演習テンプレ

S2 ハンズオンで配布する形式:

```
お題: <業務シーン>
悪い: <雑な依頼の例>
良い: <4 原則を満たした依頼の例>
解説: どの原則をどう適用したか
```

例:

```
お題: ある関数が遅いので速くしたい
悪い: 「遅いから速くして」
良い:
  - 目的: 「`process_orders()` の p95 を 200ms 以下にしたい」
  - コンテキスト: 「現状 800ms。`orders` テーブルを N+1 で叩いている」
  - 検証: 「`pytest -k bench_orders` で p95 を出力。基準値以下で合格」
  - 分解: 「まずクエリプランを確認 → ボトルネック特定 → 修正案を 2 つ提示」
```

---

## 落とし穴

- **長すぎるプロンプト**: 5 段落超えたら別チャンクに分解
- **複数の依頼を 1 文に詰める**: 「Aして、Bして、Cもよろしく」→ 分けて頼む
- **否定形だけで指示**: 「〇〇しないで」だけだと逆に意識が向く。**「代わりに何をすべきか」** をセットで
- **検証コマンドを指定しない**: 完了報告が信用できなくなる

---

## まとめ

| 原則 | 一言で |
|---|---|
| 目的を明確に | 結果を誰でも同じに描けるか |
| コンテキストを与える | どこ・何を・どう を埋める |
| 検証可能な形で頼む | 完了基準をコマンドで書く |
| 分解する | 1 タスク 1〜3 ファイル |

→ この 4 つを意識するだけで、生成物の品質が体感で 2 倍以上変わる。
